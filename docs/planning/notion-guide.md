# PLANNIT Notion 운영 가이드

이 문서는 PLANNIT 팀 Notion을 만들고 운영하기 위한 기준이다. 처음부터 복잡하게 구성하지 않고, 팀원이 현재 상태와 다음 할 일을 빠르게 확인할 수 있는 구조를 우선한다.

## 1. 전체 페이지 구조

```text
🏠 PLANNIT 홈
├── 📌 프로젝트 개요
├── 🗺️ 로드맵
├── ✅ 작업 보드
├── 📝 회의록
├── 🎨 디자인·기능 명세
├── 🛠️ 오류 및 해결 기록
├── 🤖 AI 분석 테스트
└── 📚 팀 규칙·참고 자료
```

### 🏠 PLANNIT 홈

팀원이 Notion에 들어왔을 때 가장 먼저 보는 대시보드다.

- 프로젝트 한 줄 소개: `사진 한 장으로 시작하는 AI 일정 관리 서비스`
- 현재 개발 단계와 이번 주 목표
- 작업 보드의 `진행 중`, `막힘`, `마감 임박` 보기
- 최근 회의록
- Figma, GitHub, README 바로가기
- 팀원별 담당 작업

홈에는 모든 내용을 직접 작성하지 않고, 아래 데이터베이스의 필요한 보기만 연결한다.

## 2. 작업 보드

개발 업무를 관리하는 가장 중요한 데이터베이스다.

### 속성

| 속성 | 형식 | 작성 예시 |
|---|---|---|
| 작업명 | 제목 | 이미지 업로드 미리보기 구현 |
| 분야 | 선택 | 기획, 디자인, Frontend, Backend, AI, Integration, Testing |
| 상태 | 상태 | 할 일, 진행 중, 검토, 완료, 막힘 |
| 우선순위 | 선택 | 높음, 보통, 낮음 |
| 담당자 | 사람 | 김래원 |
| 시작일 | 날짜 | 2026-08-28 |
| 마감일 | 날짜 | 2026-09-03 |
| 관련 기능 | 관계형 | 이미지 기반 일정 등록 |
| GitHub | URL | Issue, Commit 또는 Pull Request 링크 |
| 막힌 이유 | 텍스트 | API 응답 형식 미확정 |

### 추천 보기

- `전체 보드`: 상태별 칸반
- `이번 주`: 이번 주에 시작하거나 마감되는 작업
- `내 작업`: 담당자가 본인인 작업
- `마감 임박`: 마감일이 3일 이내이면서 완료가 아닌 작업
- `막힘`: 상태가 `막힘`인 작업
- `개발 일정`: 시작일과 마감일을 사용하는 타임라인

### 상태 이동 기준

```text
할 일 → 진행 중 → 검토 → 완료
          ↓
         막힘
```

- `검토`: 기능 구현은 끝났지만 테스트나 팀원 확인이 필요한 상태
- `완료`: 구현, 테스트, 문서 반영까지 끝난 상태
- `막힘`: 이유와 해결에 필요한 사람 또는 조건을 반드시 기록

## 3. 로드맵

큰 기능과 개발 단계를 관리한다. 세부 코드는 작업 보드에서 관리하고, 로드맵에는 사용자에게 보이는 결과 중심으로 적는다.

### 속성

| 속성 | 형식 | 예시 |
|---|---|---|
| 기능명 | 제목 | AI 일정 분석 |
| 단계 | 선택 | 기획, 개발, 통합, 테스트, 완료 |
| 우선순위 | 선택 | MVP, 다음 버전, 아이디어 |
| 목표 기간 | 날짜 범위 | 2026-08-01 ~ 2026-09-30 |
| 담당자 | 사람 | 김래원, 김윤수 |
| 관련 작업 | 관계형 | Gemini 응답 스키마 설계 외 3건 |
| 완료 조건 | 텍스트 | 이미지에서 일정 추출 후 수정 가능 |

### MVP 기능 순서

1. 이미지 업로드, 형식·크기 검증, 미리보기
2. Gemini API 이미지 분석과 구조화된 JSON 응답
3. 분석 결과 확인·수정
4. 일정 등록·조회·수정·삭제와 캘린더 표시
5. 알림
6. 그룹 일정 공유와 권한
7. 일정 충돌과 준비 계획 자동 분배

## 4. 회의록

회의에서 이야기한 모든 내용을 길게 적기보다 결정과 다음 행동을 명확히 남긴다.

### 속성

| 속성 | 형식 | 예시 |
|---|---|---|
| 회의명 | 제목 | 8월 4주차 기능 회의 |
| 날짜·시간 | 날짜 | 2026-08-26 10:00 |
| 참석자 | 사람 | 팀원 4명 |
| 회의 종류 | 선택 | 정기 회의, 기획, 디자인, 개발, 회고 |
| 관련 작업 | 관계형 | 분석 결과 확인 화면 |

### 회의록 템플릿

```markdown
## 회의 목표

- 이번 회의에서 결정해야 하는 내용

## 논의 내용

- 핵심 의견과 근거

## 결정 사항

- 최종 결정과 선택 이유

## 할 일

- [ ] 작업명 / 담당자 / 마감일

## 다음 회의

- 날짜·시간:
- 확인할 내용:
```

회의에서 나온 할 일은 체크박스로만 끝내지 않고 작업 보드 항목으로 만든다.

## 6. 오류 및 해결 기록

반복될 수 있거나 원인을 찾는 데 시간이 걸린 문제를 기록한다.

### 속성

| 속성 | 형식 | 예시 |
|---|---|---|
| 오류 제목 | 제목 | 날짜가 하루 전으로 저장됨 |
| 상태 | 상태 | 확인 중, 해결, 재발 |
| 발생일 | 날짜 | 2026-09-10 |
| 분야 | 선택 | Frontend, Backend, AI, 배포 |
| 작성자 | 사람 | 손예준 |
| 재현 방법 | 텍스트 | 시간대 없는 날짜를 등록 |
| 원인 | 텍스트 | UTC 변환 과정에서 시간대 누락 |
| 해결 방법 | 텍스트 | ISO 8601과 Asia/Seoul 적용 |
| 관련 작업·코드 | URL/관계형 | GitHub 링크 |

API 키, 비밀번호, 개인정보, 안내문 원본 내용은 오류 기록이나 캡처에 넣지 않는다.

## 7. AI 분석 테스트

Gemini 분석 품질을 같은 기준으로 비교하기 위한 데이터베이스다.

### 속성

| 속성 | 형식 | 예시 |
|---|---|---|
| 테스트명 | 제목 | 표 형식 수행평가 안내문 |
| 문서 유형 | 선택 | 시험, 수행평가, 과제, 학사 공지, 손글씨 |
| 이미지 품질 | 선택 | 선명함, 흐림, 기울어짐, 어두움 |
| 기대 일정 수 | 숫자 | 3 |
| 실제 일정 수 | 숫자 | 2 |
| 결과 | 선택 | 성공, 부분 성공, 실패 |
| 틀린 필드 | 다중 선택 | 제목, 날짜, 시간, 장소, 준비물, 상세 내용 |
| 모델·프롬프트 버전 | 텍스트 | prompt-v1 |
| 관련 오류 | 관계형 | 두 번째 날짜 누락 |
| 테스트일 | 날짜 | 2026-09-15 |

학생 이름, 연락처 같은 개인정보가 포함된 이미지는 가리거나 테스트용 문서로 바꾼 뒤 올린다. 실제 API 키와 전체 AI 응답의 민감 정보도 Notion에 저장하지 않는다.

## 8. 팀 규칙·참고 자료

한 페이지에 아래 내용을 모아 둔다.

- 변수명과 함수명은 `camelCase`
- 함수 위에 입력값, 출력값, 기능 요약 주석 작성
- AI 결과는 서버 검증과 사용자 확인 후 저장
- Gemini API 키는 서버에서만 사용하고 GitHub·Notion에 기록하지 않음
- 일정은 ISO 8601, 기본 시간대는 `Asia/Seoul`
- 완료된 기능만 README와 Notion에서 `완료`로 변경
- GitHub 브랜치, 커밋, 코드 리뷰 규칙
- Figma, GitHub, README, 공식 API 문서 링크

## 10. 운영 습관

- 작업을 시작할 때 담당자, 마감일, 상태를 입력한다.
- 작업이 끝나면 GitHub 링크와 테스트 결과를 남긴 뒤 `검토`로 이동한다.
- 팀원이 확인한 뒤 `완료`로 이동한다.
- 회의가 끝나면 결정 사항과 할 일을 작업 보드에 연결한다.
- 매주 한 번 `막힘`, `마감 임박`, 오래된 `진행 중` 작업을 함께 확인한다.
- README의 개발 현황과 Notion의 상태가 다르면 실제 구현과 검증 결과를 기준으로 맞춘다.
